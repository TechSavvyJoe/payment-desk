# Workspace upgrade research

Research for improving the existing Payment Desk web worksheet and Chrome companion within the current device-only release. Reviewed October 11, 2026. This is a product-gap assessment, not a tax, lending, legal, or vendor-integration specification.

## Scope and evidence

The project README and [Product Experience Refinement](PRODUCT-EXPERIENCE-REFINEMENT.md) describe a Michigan resident retail cash/finance estimator, guarded customer exports, browser-local worksheet drafts, and a Chrome side panel with optional public-inventory capture/catalog. The implementation does not have a saved-deal backend, cross-device sync, tax provider, lender connections, contracting, or customer record workflow. Recommendations below stay within those boundaries.

Vendor materials are first-party descriptions of their own products. They show common workflow patterns and stated capabilities; they do not independently establish outcomes, market-wide standards, or access available to Payment Desk.

## Prioritized gaps and feasible improvements

| Priority | Workflow evidence and current gap | Feasible improvement in this release | Boundary |
| --- | --- | --- | --- |
| P1 — Make a quote handoff easier to resume | DealerCenter describes a flow from vehicle and trade through terms/rate/down-payment comparisons, then a printable/email quote; it also describes moving from quote into a separate deal workflow. Payment Desk already has vehicle/deal inputs, comparison grid, customer view, and export actions, but no transaction record or explicit handoff checklist. | Add a compact, printable “review with customer” checklist to the existing estimate: vehicle/price and availability confirmed, trade/payoff confirmed, selected term/rate/down payment reviewed, registration amount verified, and estimate assumptions acknowledged. Keep it an on-screen/print checklist, not persisted buyer data. | A checked item records staff review only; it is not lender approval, legal disclosure, contract readiness, or external delivery proof. [DealerCenter source](#sources) |
| P1 — Clarify payment scenario comparison | DealerCenter documents a terms/rates/down-payment matrix and print quote; Dealertrack’s product flyer claims side-by-side quote negotiation and multiple loan/lease quote workflows. Payment Desk has a guarded grid and a target/limits tool already. A user can still benefit from a clearer side-by-side explanation of what changes between selected and comparison scenarios. | Tighten the existing comparison rows to foreground only the differing term, assumed rate, payment, cash due, and estimated total interest; retain the current “assumption” language and explicit Apply/Undo behavior. Add a concise “same vehicle, trade, products, and fees” caption where the results appear. | Do not present rates as lender offers, imply approval, or add lease options; leases are explicitly out of scope. Vendor statements describe their products. |
| P1 — Improve draft continuity without cloud claims | The web draft and companion draft are separate. Browser site data can be removed, and Chrome extension local storage is machine-local and cleared when the extension is removed. Users can mistake auto-save for backup. | Add an explicit, user-initiated **Export draft** / **Import draft** file flow for the existing worksheet draft, with schema/version validation, preview before replacement, and visible success/failure. Include no analytics or upload. If that is too large for this release, improve the current save indicator with a direct “saved on this device” explanation and a one-step reminder to export/print before reset or device changes. | File export is user-managed backup and may contain financial/deal details. Do not add sync, server storage, customer PII, or claim that local saves cannot be evicted. Keep website and extension drafts separate unless a deliberate reviewed transfer flow is specified. |
| P2 — Make entry faster and reduce correction work | Apple recommends clear field labels/hints, choices where practical, and prompt validation with actionable correction guidance. The existing app already has targeted recovery for invalid or missing fields. | Favor compact pickers or presets for repeated bounded choices (for example, common financing terms) while preserving typed entry where supported. Keep errors adjacent to fields, name the correction, and preserve unfinished typing as the current draft rules require. | Defaults are convenience only; they must not silently alter committed deal figures or become lender/dealer policy. |
| P2 — Improve customer-facing access and readability | Apple’s accessibility guidance says information should not rely on a single visual cue and recommends readable text, sufficient contrast, and comfortably sized controls. The refinement already establishes keyboard focus, text-plus-color status, and mobile layouts; the next product increment should validate the real estimate at zoom and with assistive technology. | Prioritize a focused accessibility pass over the estimate, grid, and recovery dialogs: verify label/value association, reading order, keyboard-only completion, focus after errors/actions, browser zoom/reflow, contrast, and visible focus. Add text equivalents for status and ensure the printed/PDF estimate keeps labels attached to values. | These are review targets, not a claim that the current interface fails them. Keep scope to existing flows; no broad redesign is implied. |
| P2 — Explain inventory freshness at the decision point | The companion already marks partial refreshes, retained catalogs, and last-seen state; its README warns that coverage is connector-specific. A vehicle chosen from a cached catalog may still be unavailable or repriced. | In the selected-vehicle review step, carry the observed source and last-seen timestamp next to the fields and require staff confirmation of current selling price/availability before applying it to a new estimate. | Capture remains public listing data only. Do not crawl authenticated pages, claim complete inventory, or auto-apply a listing over an existing deal. |
| P3 — Keep scope and local-data boundaries visible | The README correctly limits the tax model to Michigan and states that local drafts can be erased. A workspace upgrade can accidentally make “saved,” “tax,” or “payment options” sound more authoritative than the underlying model. | Reuse a short, consistent scope line at the estimate and export boundary: Michigan supported scope; estimate only; verify current vehicle, fees, and terms; draft saved on this device. Keep unsupported jurisdiction/transaction blocks actionable and explicit. | Do not add nationwide selector behavior, tax/title/registration APIs, lender matching, credit pulls, or fabricated backend statuses. |

## Recommended order

1. Improve the comparison and review/print handoff using the current guarded worksheet and existing output formats.
2. Add device-local draft export/import only if the product owner wants a portable backup in this release; otherwise make save and deletion limits unmistakable.
3. Validate accessibility and inventory freshness in the actual customer-estimate and vehicle-selection flows.
4. Keep any provider, lender, account, customer-record, or multi-state capability behind separate requirements and acceptance gates.

This ordering favors changes that reduce in-store confusion and recovery risk without changing the calculator’s jurisdiction, tax assumptions, or data architecture.

## AutoIQ calculator suitability

The callable **AutoIQ `auto_loan_calculator`** capability is a ChatGPT interactive calculator. Its tool metadata accepts price, down payment, APR, term, trade value/payoff, incentives, tax percentage/state, and title fees, and returns payment/loan summary values. The official [ChatGPT app listing](https://chatgpt.com/plugins/plugin_asdk_app_69c985207afc8191aff0489b7c70e7eb) describes payment, tax/fee, and amortization exploration and names Layer3Labs as developer. This makes it a useful **workflow reference** for input coverage and explanation of payment changes.

The surfaced callable capability and public listing do not document a dealer-facing API, embeddable widget, licensing terms, integration agreement, or authoritative tax-data source. The separate [AutoIQ.com Express Shop workflow](https://www.autoiq.com/how-it-works/) describes that retailer’s customer purchase journey, but does not establish that it is the same product or that its calculator can be licensed or embedded. Therefore AutoIQ is **not currently evidenced as a feasible licensed integration** for Payment Desk. Its consumer/ChatGPT calculator must not be treated as Michigan tax authority or as a substitute for the project’s reviewed policy/provider gate. No widget was launched and no deal or customer data was sent.
